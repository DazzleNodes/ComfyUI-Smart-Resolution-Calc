# Human Test Checklist: Widget restore and scale on ComfyUI frontend 1.53

**Target version:** v0.12.5
**Ships with commit:** TBD (fix: widget restore, scale and scale steps on frontend 1.53, #60, on top of PR #59)
**Companion automated tests:** 94 unit tests in `tests/unit/` (Serialization.test.js 11 new, others unchanged); live e2e: `widget-restore-frontend-153.spec.js` 6 new, `seed-dragin.spec.js` 4, `seed-reload.spec.js` 5, `seed-metadata.spec.js` 1, smoke 5. Red-green audit of the 17 new tests: 11 anchors, 6 backward-compatibility guards.

## What this is

ComfyUI frontend 1.53 changed how node widgets are saved and restored. It writes its own name-keyed copy of widget values, renames duplicate widget names to `name#1`, and saves only an allowlist of node keys. SmartResCalc broke in three ways: a reloaded workflow or dragged-in image showed stale height and seed values, the scale slider never reached Python (1.5x on 1400 produced 1400), and custom scale step sizes were lost on save. v0.12.5 fixes all three and includes PR #59, which finds the scale slider by a retained reference because the frontend swaps custom widgets' prototypes. This checklist covers what the live tests cannot: real drag-in of images, real generation at a scale, the step-size panel clicks, and older frontends.

## Prerequisites

1. ComfyUI at `http://localhost:8188` with a 1.53.x frontend (Settings > About shows the version), serving this checkout's `web/`. Hard-refresh (Ctrl+Shift+R) after installing.
2. Optional debug logging, in the browser console, then hard-refresh:
   ```javascript
   localStorage.setItem('DEBUG_SMART_RES_CALC', 'true')
   ```
3. A model workflow that feeds SmartResCalc's width/height or latent into a sampler and saves an image. HV.3 generates one image; every other step only loads and saves.
4. **State isolation:** work in a spare workflow tab and save test workflows under a throwaway name. Nothing here changes ComfyUI settings.

**Reset between sections:** close the test tab and open a fresh one.

## High-Value Verification (~5 minutes)

### HV.1 — A dragged-in image restores the height it was generated with

Validates: the frontend's own name-keyed block wins over the node's older one on restore.

- [ ] **Steps:** drag in an image generated under frontend 1.53 with a height that differs from the node default (for example 2096).
- [ ] **Expected:** the node's HEIGHT widget shows the generated height, not an older value such as 1216. With debug logging the console shows `[configure] Name-based restore complete (source: widgets_values_named)`.
- [ ] **Why this matters:** this was the reported symptom; the wrong height silently changes every re-run.

### HV.2 — A random seed reloads as random

Validates: the seed's display state comes from the frontend block, not a stale locked seed.

- [ ] **Steps:** drag in an image generated with the seed in random mode.
- [ ] **Expected:** random mode (dice lit), the value box shows the image's own seed dimmed, recycle available. Queueing produces a new seed, not a repeat of an old one.
- [ ] **Why this matters:** a stale locked seed reproduces an old image instead of rolling a new one.

### HV.3 — Scale reaches Python (generates one image)

Validates: the hidden `scale` input carries the slider's value into the prompt.

- [ ] **Steps:** set base height 1400, scale 1.5x, queue once.
- [ ] **Expected:** the output is 2096 px high (2100 rounded to the divisible-by setting). With 1.2x it is 1680.
- [ ] **Why this matters:** before this fix Python always received 1.0 on 1.53 and the slider did nothing.

### HV.4 — Scale survives save and reload

- [ ] **Steps:** set scale 1.5x, save the workflow, close the tab, open the saved workflow.
- [ ] **Expected:** the slider shows 1.5x. Queueing without touching it still produces the scaled size.
- [ ] **Why this matters:** the slider itself is no longer saved; the hidden input is, and the slider must adopt it on load.

### HV.5 — Custom scale step sizes survive save and reload

- [ ] **Steps:** open the scale slider's settings (gear icon), change the left and right step sizes with the +/- buttons and by clicking a value to type one, save, reload.
- [ ] **Expected:** the settings panel shows the same step sizes after reload, and dragging the slider moves in those steps.
- [ ] **Why this matters:** before this fix the steps were saved only through a hook that frontend 1.53 does not call.

### HV.6 — Saved files carry no stale copy

- [ ] **Steps:** load an image from before this fix, then File > Export the workflow and open the JSON in a text editor.
- [ ] **Expected:** the SmartResCalc node has `widgets_values_named` and no `widgets_values_by_name` (neither at the top level nor under `extensions`). Scale steps appear under `properties.dazzle_scale_steps` once set.
- [ ] **Why this matters:** the stale copy was echoed back on every save and was the source of HV.1's wrong values.

## Section 1: Older files (~3 min)

- [ ] **A workflow saved by v0.12.4 or earlier on an older frontend** (only the node's own name-keyed block): loads with its saved values; the console reports `source: widgets_values_by_name`.
- [ ] **A workflow saved on 1.53 before this fix** (the slider stored as `scale#1`): loads with the slider at the value the user had set, not 1.0.
- [ ] **A workflow with step sizes in the pre-0.12.5 `widgets_config` block**: the steps restore, and after one save they appear under `properties.dazzle_scale_steps`.

## Section 2: PR #59 paths (~2 min)

- [ ] **Image disconnect clears the cached image dimensions:** connect an image, note that the scale tooltip or dimension readout uses its size, disconnect it. The readout falls back to the widget dimensions, with no console error.
- [ ] **Mode readout follows scale:** with an image connected, change the scale; the MODE line updates without errors.

## Section 3: Older frontends (MANUAL, only if one is available)

- [ ] On a ComfyUI install with a frontend before 1.5x, repeat HV.1 to HV.5. Expected: the same results. There, the node writes and reads its own name-keyed block, and the slider is found by name as before.
- [ ] Open a workflow saved on 1.53 with that older frontend. Values restore by position; expect them to match unless the node's widget list changed between the two versions.

## Section 4: Automated runs (~3 min, same commands in every shell)

- [ ] `npx vitest run` gives 94 passed (5 files).

- [ ] `npx playwright test tests/e2e/smoke.spec.js tests/e2e/seed-dragin.spec.js tests/e2e/seed-reload.spec.js --reporter=list` gives 14 passed.

## What the automated tests DON'T cover

- Real drag-and-drop and File > Open of images (HV.1, HV.2); the tests load workflow JSON.
- Real generation at a scale (HV.3); the tests read the prompt payload, not the output image.
- The settings panel clicks and typed values for step sizes (HV.5); the test assigns the values and calls the change hook the handlers call.
- Older frontends (Section 3); only 1.53.6 is installed on the test machine.
- The new blend_strength tooltip text: hover it and judge whether it reads clearly.

## Reporting issues found

1. Note the section and step, and the frontend version from Settings > About.
2. Paste the `[configure]` console lines (debug logging on) and, for save problems, the exported workflow's SmartResCalc node.
3. File an issue referencing this checklist, v0.12.5 and #60.

## Cleanup

- `localStorage.removeItem('DEBUG_SMART_RES_CALC')` in the console, then hard-refresh.
- Delete the throwaway workflows and the HV.3 image if you do not want to keep them.
